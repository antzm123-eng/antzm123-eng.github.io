## 이미지

### 원본을 1600px 로 제한한다
무단 인쇄 사용을 막기 위해서. 1600px 는 A4 300dpi 인쇄에 한참 못 미치지만
화면으로 보기에는 충분하다. 2160~5000px 였던 85장을 축소.
**되돌리지 말 것** — 원본 화질을 지키려고 크기를 올리면 저작권 방어가 무력해진다.

### 썸네일은 700px
처음 정할 때 목록 표시 크기가 176px 이어서 2~3배 화면까지 충분했다.
**2026-09-01 카드 구조를 바꾸면서 표시 크기가 277~623px 로 커져 이 전제가 깨졌다.**
641~800px 구간에서는 2배 화면 기준 해상도가 56% 로 부족하다(다른 폭은 93~100%).
지금은 용량과의 절충으로 700px 을 유지하되, 선명도를 올리려면 1280px 재생성이 필요하다.

### 투명 배경 PNG 는 JPG 로 바꾸지 않는다
JPEG 는 투명도를 지원하지 않아 로고가 **검은 네모**가 된다.
실제로 `na_logo` 3장은 투명 픽셀이 77~97% 였다.
`hasAlpha` 플래그만 믿으면 안 된다 — 포토샵 내보내기는 불투명해도 `yes` 로 나온다.
**픽셀을 직접 검사**해서 판단할 것 (0.5% 이하면 사실상 불투명).

### 저작권 정보는 바이트 단위로 삽입한다
`sips -s copyright` 를 쓰지 않는 이유:
- JPEG 79장에서 아예 실패했다 (기존 EXIF 가 있는 파일)
- 성공해도 **이미지를 재인코딩**해서 용량이 늘고 화질이 나빠진다 (3.8MB → 5.2MB)

그래서 JPEG 는 COM 세그먼트, PNG 는 iTXt 청크를 직접 끼워 넣는다.
화질·용량 변화가 전혀 없고, 카메라 EXIF(저작권 증거)도 보존된다.

**이미지를 재인코딩하는 작업 뒤에는 반드시 저작권 정보를 다시 넣을 것.** 재인코딩하면 지워진다.

## 워터마크

### 문구는 `H_yun_9u`, NA 로고가 아니다
NA 로고는 사역 브랜드이고, 이 포트폴리오는 **개인 작업물**이기 때문. 사용자 결정.

### 불투명도 60% (은은함 42% / 확실함 80% 중)
세 강도를 실제 사진에 얹어 비교한 뒤 사용자가 선택.
밝은 아스팔트 배경에서도 읽히도록 옅은 그림자를 함께 넣는다.

### 위치는 오른쪽 아래
사진 워터마크의 관례. 포스터에 넣었을 때 기존 로고와도 부딪히지 않았다.

### 썸네일에는 넣지 않는다
표시 크기가 176px 라 글자가 뭉개지고 목록만 지저분해진다.
**저장해 가는 대상은 크게 보기 이미지**이므로 거기만 보호하면 충분하다.

### 커버는 `images/full` 의 아래 7% 를 잘라 만든다 (2026-09-02)
카메라 원본을 사용자가 지웠으므로 커버를 되살릴 재료는 `images/full` 뿐인데,
거기엔 워터마크가 합성돼 있다. 워터마크는 오른쪽 아래·짧은 변의 6.6% 안에 들어오므로
**아래쪽만 잘라내면 사라진다** (오른쪽을 자르면 16% 를 버려야 해서 손해가 크다).

- 사진은 아래 7% 가 대개 배경이라 잃는 것이 적고, **커버는 어차피 `object-fit:cover` 로 잘린다.**
- 얻는 것: 레티나 최저 선명도 28% → 83%, 21장 중 19장이 100%.
- **라이트박스는 손대지 않는다.** 작품을 판단하는 곳은 거기이고, 원본은 그대로 남는다.

**포스터는 예외 — 자르지 않는다.** 아래쪽에 로고와 성경 구절이 들어 있어 디자인이 망가진다.
사용자가 직접 만든 것이니 작업 파일이 나오면 그때 자르지 않고 교체한다.
목록은 `regen_covers.py` 의 `FULL_SKIP` 에 있다.

### JPEG 품질 0.80
워터마크를 구우려면 재인코딩이 불가피하다. 0.70~0.88 을 비교한 결과
0.80 이 화질 대비 용량 균형점. 원본보다 용량이 늘어나는 건 감수한다
(크게 보기는 한 번에 한 장만 불러오므로 첫 화면 속도에 영향 없음).

## 코드

### `nav` 에 `backdrop-filter` 를 걸지 않는다
`backdrop-filter` 는 자식의 `position:fixed` 기준점을 화면이 아닌 **그 요소의 박스**로 바꾼다.
그래서 모바일 메뉴 패널이 nav 높이(86px) 안에 갇혔다.
blur 를 `nav::before` 로 옮겨 해결. **nav 에 `filter`/`transform` 계열을 추가하지 말 것.**

### 라이트박스 배경 잠금은 `body{position:fixed}` 방식
`overflow:hidden` 은 프로그램 스크롤을 막지 못한다.
`position:fixed` 는 확실히 막지만 스크롤바가 사라지며 레이아웃이 밀린다
→ `scrollbar-gutter:stable` 로 해결하고, 미지원 브라우저를 위해 JS 폭 보정도 남겨뒀다.
지원 브라우저에서 둘 다 적용하면 **이중 보정**이 되므로 `CSS.supports` 로 분기한다.

### 포커스 이동은 `preventScroll:true`
포커스를 옮기면 브라우저가 그 요소를 화면 안으로 끌어와 위치가 틀어진다.
라이트박스를 열고 닫을 때 반드시 필요.

### 푸터는 하나만 둔다
원래 있던 미니 푸터를 못 보고 새 푸터를 추가해 중복됐던 적이 있다.
또 `footer{display:flex}` 규칙이 새 푸터에도 적용돼 레이아웃이 깨졌다.
현재는 하나로 통합하고 `.site-footer{display:block}` 으로 덮어쓴다.

## 구조

### 경력은 Work 그리드가 아닌 별도 `#career` 섹션
Work 카드는 미리보기 사진 4장이 핵심인데, 사진 없는 카드가 끼면 그 자리가 비어 휑해 보인다.
사진첩과 이력서는 성격이 다르므로 분리한다. (2026-08-31 구현 완료)

### 경력의 회사명은 사용자가 정한 범위까지만 쓴다
계약상 업무 공개 제한이 있을 수 있어 공개 범위를 먼저 물었고, 사용자가 사명 대신
업종(`식물 기반 사회적기업`)으로 보내왔다. 임의로 추정해 채우지 않고 그대로 쓰되,
제목 옆에 `사명 비공개` 칩을 달아 **빠뜨린 게 아니라 의도적 비공개**임을 보이게 했다.
앞으로 경력을 추가할 때도 회사명 공개 여부를 먼저 확인할 것.

### 경력의 AI 도구 사용은 숨기지 않고 '구분해서' 적는다
이 사이트는 AI 학습 금지를 강하게 내걸고 있어(`noai` 메타, 크롤러 24종 차단, 푸터 문구),
경력란의 `AI 도구` 칩이 "사진도 AI로 만든 것 아니냐"는 오해를 부를 수 있었다.
칩을 지우면 실제 역량이 사라지므로, **툴 이름을 명시하고 용도를 라벨로 못 박은 뒤
"사진·디자인 작업물은 직접 제작"이라는 주석을 붙이는** 방향을 택했다.

### 경력 수치는 확인 전까지 푸시하지 않는다
사용자가 보내온 성과 수치는 실제 기록이 아니라 추정치였다("~라고 가정 시").
포트폴리오의 숫자는 면접에서 반드시 되물어보므로, 막히면 나머지 진짜 경력까지
의심받는다. 본문에는 반영하되 **각 수치를 표로 되돌려 확인받는 절차**를 넣었다.

### 작업 목록을 `works.json` 으로 분리하지 않는다 (당분간)
관리는 편해지지만 `index.html` 을 **더블클릭으로 열었을 때** 브라우저 보안 정책 때문에
JSON 을 못 읽어 사진이 안 뜬다. 사용자의 확인 방법이 파일 직접 열기이므로 지금은 부적합.
`add_work.py` 가 이미 자동 등록해주므로 불편하지도 않다.
**인터넷 공개 이후 재검토할 것.**

### 호스팅은 Netlify 가 아니라 GitHub Pages
이 사이트는 빌드가 없는 정적 HTML 한 장이고, Netlify 고유 기능(폼·서버리스 함수·
리다이렉트·비밀번호)을 **하나도 쓰지 않는다.** 그런데 Netlify 무료 플랜은 배포 1회에
15크레딧(월 한도 300의 5%)을 물리므로, 작업물을 추가할 때마다 비용이 발생한다.
GitHub Pages 는 공개 저장소에서 무료이고 배포 횟수 제한이 없으며 대역폭도 6.7배 넉넉하다.
`canonical`/`og` 태그가 이미 GitHub Pages 주소로 적혀 있던 것도 이유가 됐다.
**폼이나 서버 기능이 필요해지면 그때 재검토.**

### 작업 카드는 대표 사진 1장을 크게 (썸네일 5개 나열 아님)
썸네일 5개를 한 줄에 늘어놓으면 한 장이 53px 로 표시된다. 사진가의 사이트에서
작품이 우표 크기가 되는 것은 치명적이다. 대표 1장을 크게 보여주고 나머지는
배지 + 라이트박스로 넘긴다. 사진은 5배 커지고 첫 화면 전송량은 76% 줄었다.

### 커버 프레임은 이미지 실제 비율로 나눈다
하나의 비율로 고정하면 세로 포스터가 40% 잘린다. 포스터는 구도 자체가 작품이므로
잘라내면 안 된다. 커버마다 `data-ratio` 를 심어 가로 3:2 / 정사각 1:1 / 세로 4:5 로
나눈다. 카드 높이가 조금씩 달라지지만 **작품을 자르는 것보다 낫다.**
작업물을 추가할 때도 이 규칙을 유지할 것.

### 경력 섹션 서술 규칙 (경력 문구를 고치기 전 반드시 읽을 것)

**사명 비공개.** 현재 항목은 `식물 기반 사회적기업` + `사명 비공개` 칩으로 표기한다.
재직 중이므로 유지하고, **퇴사가 정해지면 그때 공개 여부를 다시 묻는다.**
사명·공간명·지역은 본문에 넣지 않는다. 회사에서 만든 작업물도 공개 불가.

**역할 비중.** 회사는 **교육 / 공간기획·조성** 두 축이고 사용자의 주력은
**공간기획·조성**, 교육은 **보조**다. 담당 업무와 성과의 순서를
`공간기획 → 브랜드 마케팅 → 교육(보조)` 로 둔 이유이며, 바꾸면 사실과 어긋난다.
교육은 "운영을 보조했고" 로 쓰되 설문 통계·보고서는 본인 주도이므로 그대로 둔다.

**"운영"이라는 말의 범위.** 조직은 대표 / 사용자(기획·마케팅·브랜딩·공간) /
카페 총괄매니저 2명 / 아르바이트생으로 구성된다. **사용자는 카페의 현장 운영
(매출·재고·인력)에 관여하지 않는다.** 그래서 "운영"을 쓸 때는 `공간 운영` 처럼
범위를 한정한다. 아르바이트 채용도 대표와 총괄매니저가 하므로 인력 운영은 적지 않는다.

**조직 규모 대신 역할 범위로 밀도를 표현한다.** 처음에 "대표 포함 2인 조직"이라 적었는데
실제로는 최소 4명 + 아르바이트여서 사실과 달랐다. `기획·브랜딩 전담 1인` 은 인원이
늘고 줄어도 변하지 않고, 면접에서 되물어도 답이 막히지 않는다.

**수치는 검증 가능한 것만.** 사용자가 보낸 초안에는 추정치가 섞여 있었다.
근거 자료가 없던 설문 만족도(4.8점)는 삭제했고, 평수·주도 범위는 실제에 맞게 정정했다.
포트폴리오의 숫자는 면접에서 반드시 되물으므로 **검증 불가능한 수치는 넣지 않는다.**

### 칼럼 경계는 800 / 1280px — 사진 크기를 기준으로 잡는다
칼럼을 억지로 늘리면 사진이 작아진다. 경계를 정할 때는 "몇 칼럼이 예뻐 보이나"가
아니라 **"그 폭에서 사진이 몇 px 로 보이나"** 를 기준으로 판단할 것.
641px 에서 2칼럼을 시도했더니 사진이 204px 로 쪼그라들어 되돌렸다.
현재: ≤800 1칼럼 / 801~1280 2칼럼 / 1281 이상 3칼럼(1500 이상은 3칼럼 고정).
**중단점을 새로 만들 때는 반드시 그 폭에서 사진 표시 크기를 재볼 것.**

### 이미지 포맷은 WebP 가 아니라 AVIF
이 맥에는 webp 인코더가 없고(`cwebp`/`magick`/`ffmpeg` 미설치, `sips` 미지원),
CoreGraphics 는 AVIF 를 지원한다. AVIF 가 압축률도 더 좋다.
**결정적인 이유는 저작권이다** — `CGImageDestinationAddImage` 에 TIFF/IPTC 딕셔너리를
넘기면 변환과 동시에 저작권이 심긴다. 기존 JPEG 재인코딩 방식의 고질적 문제
(저작권 소실 → 사후 재삽입)가 사라진다.

### 원본 JPEG/PNG 를 지우지 않는다
AVIF 미지원 브라우저(약 5%)를 위한 폴백이다. 저장소가 93MB→117MB 로 늘지만
GitHub Pages 한도 1GB 의 12% 수준이고, 방문자는 둘 중 하나만 받으므로
**대역폭은 늘지 않는다.**

### AVIF 인코딩 전에 가로·세로를 짝수로 자른다 (2026-09-02)
CoreGraphics 의 AVIF 인코더는 원본이 큰 사진을 타일(grid)로 나눠 인코딩하는데,
가로·세로 중 하나라도 **홀수 픽셀**이면 타일 경계 계산이 어긋난 파일을 만든다.
`sips`(Apple 자체 디코더)는 관대하게 열어줘서 맥에서는 문제가 안 보이지만,
브라우저가 실제로 쓰는 libavif 계열 디코더는 "Invalid image grid" 로 거부한다.
1px 씩 밀어가며 재현해 짝수/홀수만이 유일한 변수임을 확인했다. `to_avif.swift` 가
인코딩 직전에 짝수로 잘라 원천 차단한다(최대 1px 차이, 육안 무영향). 원본 JPEG 는
그대로 두고 AVIF 출력만 보정하므로 `<picture>` 의 두 소스 폭이 1px 어긋날 수 있는데,
`srcset` 의 `w` 는 반응형 선택용 힌트일 뿐이라 문제되지 않는다.

### 라이트박스는 AVIF 지원 여부를 '기다리지' 않는다
비동기 지원 감지 후 분기하도록 만들었더니, 감지가 끝나기 전에 첫 장이 열려
JPEG 가 나갔다. **AVIF 를 먼저 시도하고 `onerror` 로 원본에 복귀**하는 방식이
한 박자도 늦지 않고 확실하다.

### 검사할 때는 전환 애니메이션을 끄고 잰다
미리보기 창이 숨겨져 있으면 CSS 전환이 멈춰 있어, 모바일 메뉴나 포커스 스타일이
고장난 것처럼 보인다. `*{transition:none!important}` 를 주입한 뒤 측정할 것.

### `.nojekyll` 을 둔다
GitHub Pages 는 기본적으로 Jekyll 로 파일을 가공한다. 이 사이트는 가공이 전혀 필요 없고,
Jekyll 이 밑줄로 시작하는 이름을 건너뛰는 등 예상 못 한 동작을 할 수 있어 꺼둔다.

### 브랜치를 만들지 않고 `main` 에 직접 커밋
저장소 이력 전체가 `main` 직접 커밋이고, 1인 저장소다.
브랜치를 만들면 GitHub Desktop 에서 병합 단계가 늘어 사용자에게 부담이 된다.

## 운영

### 푸시는 Claude 가 하지 않는다 (할 수 없다)
GitHub Desktop 이 인증 토큰을 앱 내부에만 보관해서 터미널 git 이 인증하지 못한다.
`git push` 는 `could not read Username` 으로 실패한다.
**커밋까지만 하고 사용자에게 `Push origin` 클릭을 안내할 것.**

### 인터넷 공개 — 이미 되어 있다 (2026-09-01 기준)
원래는 작업물을 다 올린 뒤 공개할 계획이었으나, 실제로는 Netlify 로 계속 공개 중이었고
지금은 GitHub Pages(`https://antzm123-eng.github.io/gloudy/`)로 서비스한다.
`og:image` 도 이 주소 기준이며, 개인 도메인을 쓰게 되면 해당 주소만 바꾸면 된다.

**⚠️ `robots.txt` 가 지금 주소에서는 효력이 없다.** 크롤러는 `robots.txt` 를 **도메인 루트**
(`antzm123-eng.github.io/robots.txt`)에서만 읽는데 그 주소는 404 다. 우리 파일은
`/gloudy/robots.txt` 에 있어 읽히지 않는다. 즉 **AI 크롤러 24종 차단이 작동하지 않는다.**
`noai`·`noimageai`·`tdm-reservation` 메타 태그는 페이지마다 붙어 있어 그대로 작동한다.
해결안: `antzm123-eng.github.io` 라는 이름의 저장소를 새로 만들어 그 안에 `robots.txt`
하나만 두면 도메인 전체에 적용된다(무료). 또는 개인 도메인을 붙인다.

### 삭제는 휴지통으로만
중복 파일 1.2GB 를 정리할 때도 완전 삭제가 아닌 휴지통 이동을 썼다.
휴지통 비우기는 사용자가 직접 한다.
