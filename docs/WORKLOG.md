## 2026-09-07 (심야) — 열람실 숫자가 걸러낸 결과를 따라가게 고침

사용자가 발견한 오류. **목록엔 1건인데 옆 숫자는 9** 라서 "나머지 8개는 왜 안 뜨지,
아니면 오류인가" 로 읽혔다. 새 작업물 없음 — 73건·338장 그대로.

### 원인

`applyFilter()` 가 **가운데 「작업 N건」 하나만** 다시 썼다. 나머지 숫자는 HTML 에
박힌 고정값이라 무엇을 누르든 영원히 안 변했다.

### 무엇을 했나

숫자의 **뜻을 바꿨다**: 「그 해에 있는 전체 수」 → **「지금 상태에서 그걸 누르면 나올 수」**.
세는 규칙은 **자기 자신을 조건에서 뺀다** — 2023 을 고른 채 연도 숫자에까지 연도
조건을 걸면 나머지가 전부 0 이 되어 눈금이 텅 빈다.

| 어디 | 전 | 후 (`디자인` + `2023`) |
|---|---|---|
| 가운데 작업수 | 1건 (이것만 맞았음) | 1건 |
| 가운데 사진 장수 | **338장** | **8장** |
| 가운데 연도 범위 | **2023 부터 2026 까지** | **2023년** |
| 왼쪽 눈금 2023 | **9** | **1** |
| 왼쪽 눈금 막대 | 안 변함 | 숫자 ÷ 28 로 같이 줄어듦 |
| 연도 칩 `2023\|N` | **9** | **1** |
| 분류 칩 디자인 | **34건** | **1건** |
| 목록 안 연도 머리글 `.yr .n` | **18** (밑엔 2줄) | **2** |

**목록 안 연도 머리글은 1차에서 놓쳤다.** 사용자가 2차로 지적해 잡았다 —
「2024 … 18」 바로 밑에 2줄만 있는, 가장 눈에 띄는 자리였다.

**사이드바 제목도 상태를 밝히게 했다.** `.rail` 은 걸러내는 칩에서 멀리 떨어져 있어,
조건이 걸린 줄 모르고 눈금만 보면 "2024 에 2건밖에 안 했나" 로 읽힌다.
조건이 걸리면 `해마다 남긴 작업` → `고른 것만 · 해마다`.

숫자 자릿수가 바뀔 때 칩이 덜컹거리지 않도록 `.chip` 에 `tabular-nums` 를 넣었다.

**바뀌면 안 되는 숫자는 안 건드렸다** — 목차 `73`, `작업 전체 73건 보기`,
활동란 `64건·296장`. 이것들은 걸러낸 결과가 아니라 아카이브 사실이다.

### 검수

| 항목 | 결과 |
|---|---|
| **75개 조합 전수 대조**(분류3 × 연도5 × 검색5) | 어긋난 곳 **0** |
| **42번 눌러 확인** — 칩에 적힌 수만큼 실제로 나오나 | 약속 어긴 곳 **0** |
| 막대 길이 = 숫자 ÷ 28 | 어긋난 곳 **0** |
| 검사 3종 | ✅ 비공개 · 커버 · 이미지 1536개 전부 열림 |
| 가로 스크롤 | ✅ 390px 0 · 1440px 0 |

### 알아둘 것 두 가지

**① 첫 화면에서는 이 코드가 안 돈다.** `applyFilter()` 는 조건이 있을 때만 불린다
(`if(fCat !== 'all' || fYear !== 'all' || fText)`). 그래서 **HTML 에 박힌 초기 숫자는
여전히 손으로 맞춰야 한다** — 작업을 추가하면 눈금·연도칩·분류칩·`.yr .n`·머리말을
같이 고칠 것. 지금은 전부 실제와 일치한다(count_stats 로 확인). CLAUDE.md 에 적어뒀다.

무조건 호출로 바꾸면 자동으로 맞겠지만, `applyFilter` 끝에 **첫 작업을 자동 선택**하는
줄이 있어 첫 화면 동작이 바뀐다. 마무리하는 자리에서 건드리지 않았다.

**② 검수 중 두 번 헛다리를 짚었다 — 둘 다 도구 탓이었다.**
콘솔의 `ERR_CONNECTION_REFUSED` 92건은 **껐던 옛 미리보기 서버 것**이 탭에 쌓인 것
(`performance.getEntriesByType('resource')` 로 보면 이번 로드는 오류 0).
「누르는 영역 44px 미만 71개」는 **뷰어를 열어둔 채 재서** 목록 높이가 0 으로
잡힌 탓. 닫고 다시 재니 전부 정상. **재기 전에 무엇이 화면에 있는지 볼 것.**

## 2026-09-07 (밤) — 포트폴리오 사례 조사 반영 · 대표작·케이스 스터디·맥락 표기 · 새 작업물 3건

밖의 포트폴리오 사례를 조사해 우리 사이트와 대조했다. 결론은 **"코드와 디자인은
이미 상위권이고, 빈 곳은 전부 내용"** 이었다. 조사에서 반복해서 나온 지적 여섯 개를
순서대로 반영했고, 도중에 사용자가 새 작업물을 보내와 함께 올렸다.

### 무엇을 했나

**① 동두천 청년활동가 Result 신설.** 세 칸 중 여기만 Result 가 없어 "결과가 없었나"
로 읽혔다. 사용자에게 사실을 받아 3문단으로 썼다(경기문화재단 지원 사업 · 전시 1회 ·
일러스트 지도와 영상 · 4개 지역 팀). 담당 업무도 결과물 중심으로 다시 묶었다 —
"기록 촬영" 보다 **일러스트 지도·영상 편집**이 세고, 소파·조명으로 관람 공간을 꾸민
일은 회사 경력의 공간 기획·조성과 곧바로 이어지기 때문이다.

**② 활동란 단체를 숫자에서 이름으로.** `11개 단체` → **13곳 이름 나열**. 숫자는
면접에서 근거를 물으면 답해야 하지만, 이름은 사이트의 작업이 곧 근거다. 제목에
단체명이 없던 둘을 사용자가 확인해줘 11 → 13 으로 늘었다(성서인의 밤=성서대학교,
동두천 치킨캠프=신흥교회).

**③ 연락 칸에 "메일 주실 때 이 세 가지만"**(날짜·장소·어떤 자리). FAQ 는 "내가 어떻게
일하는지"를 말하므로, "그쪽이 뭘 주면 되는지" 를 그 앞에 뒀다.

**④ 대표작 8칸 신설**(`#picks`). 70건이 한 번에 열리면 강점이 희석된다는 게 조사에서
가장 자주 나온 지적이었다("방문자가 하나만 본다면 그게 내 인상이어도 괜찮은가").
지우는 대신 위에 층을 하나 더 뒀다. 70장 커버를 전부 대조표로 만들어 눈으로 보고
골랐다. 목차 `03 작업` 을 `#room` → `#picks` 로 옮겼다.

**⑤ 케이스 스터디 4건.** `DATA.why` 를 더해 뷰어에 「왜 이렇게 했나」 상자를 띄운다.

없었다. 사용자가 직접 말한 내용만 썼다.

**⑥ 작업마다 맥락 표기.** `meta` 셋째 칸이 70건 전부 `개인 작업` 이라 정보가 0이었다.
사진 37건에 전부 `촬영·보정` 을 적으면 다시 0이 되므로, **실제로 갈리는 것**을 적었다 —
`외부 단체 요청` / `소속 팀 N/A` / `개인 작업`. 목록 `data-q`(검색 색인)도 함께 고쳤다.

**⑦ 새 작업물 3건.** `analog — 사순절 플레이리스트`(2025.03) · 일산동안교회 저녁집회

## 2026-09-02 (밤 7) — 죽은 코드 정리

"지금 할 수 있는 정리를 다 진행해줘" 요청으로, 지난 감사에서 찾은 안 쓰는
폰트 굵기 외에 **CSS·JS 안에 남아있던 예전 카드 구조의 흔적**까지 전부
찾아 지웠다. 전부 2026-09-01 카드 구조 개편(썸네일 5개 나열 → 대표 사진
1장) 때 HTML에서는 지워졌지만 CSS·JS에는 안 지워지고 남아있던 것들이다.

### 지운 것

| 파일 | 무엇을 | 근거 |
|---|---|---|
| `index.html` | `@font-face` ExtraBold(800) 선언 | CSS 어디서도 `font-weight:800` 안 씀. 실제로는 다운로드도 안 되고 있었지만(브라우저가 알아서 건너뜀) 코드는 남아있었음 |
| `index.html` | `.gallery-preview`·`.g-thumb`·`.g-more`·`.more-label` CSS 4곳 | HTML 에 해당 class 를 가진 요소가 하나도 없음(전부 구버전 카드 구조 것) |
| `index.html` | `.wrap-max` CSS | 정의만 있고 어디서도 안 씀 — `section, .hero{ max-width:1560px }` 로 대체된 뒤 남은 잔재로 보임 |
| `index.html` | `.g-thumb`·`.g-more` 대상 JS 이벤트 리스너 3곳 | `querySelectorAll` 결과가 항상 빈 배열이라 실행은 됐지만 아무 일도 안 하고 있었음 |

**CSS 클래스 전수조사** — `<style>` 안 클래스 선택자 전부를 HTML `class=""` 와
JS 의 `classList`/`querySelector` 참조와 대조해서, 안 쓰는 게 더 없는지
확인했다. `#id` 선택자도 같은 방식으로 대조 — 둘 다 추가로 나온 건 없었다
(정규식이 URL 조각과 색상 코드를 클래스/아이디로 오인식한 게 전부였고,
직접 확인해 걸러냈다).

**원인**: `to_avif.swift`가 CoreGraphics로 변환할 때, 원본 사진의 **가로나 세로 중
하나라도 홀수 픽셀이면** 내부적으로 타일(grid) 구조로 인코딩하면서 깨진 파일을

항상 성공, 홀수 폭에서는 항상 실패했다.

```
1177px(홀) → 실패    1178px(짝) → 성공    1176px(짝) → 성공
852px(짝)  → 성공    853px(홀)  → 실패    854px(짝)  → 성공
```

**왜 위험한가**: `sips`는 관대해서 열리지만, 브라우저가 실제로 쓰는 libavif 계열
디코더(Chrome·Whale 포함 대부분의 Chromium)는 엄격하게 거부한다. 즉 **맥에서
확인할 땐 멀쩡해 보여도 사용자 실제 브라우저에서는 깨진 이미지로 보일 뻔했다.**

**고친 곳**: `tools/to_avif.swift` — 인코딩 직전에 가로·세로를 각각 짝수로
잘라낸다(최대 1px 차이, 육안으로 안 보임). 원본 JPEG는 안 건드리고 AVIF 출력만 보정.
이후 재현 테스트 5회 전부 성공.

**영향 범위 확인**: 기존 24개 작업물(410개 파일)은 이번 검사에서 전부 통과 —

## 2026-09-01 (8) — 검색 노출 차단 · 안 쓰는 썸네일 160장 정리

사용자가 **"지금은 검색에 안 잡히게 두고 링크로만 공유하겠다. 퇴사 시점에 공개하겠다"**
고 정했다. 그에 맞춰 3순위(크롤러)·4순위(정리)를 진행했다.

### 1. 🔴 검색 노출을 막았다 — 기존 설정이 정반대였다

`index.html` 이 `<meta name="robots" content="index, follow, noai, noimageai">` 였다.
**"검색해 가세요"** 라고 적혀 있던 것이다. 사용자 의사와 반대라 바꿨다.

```
전: index, follow, noai, noimageai
후: noindex, nofollow, noai, noimageai
```

AI 학습 거부(`noai`·`noimageai`·`tdm-reservation`)는 **그대로 유지**했다.
공개할 때 `index, follow` 로 되돌려야 하므로 HTML 주석과 `CLAUDE.md` 남은 일 2번에 적어뒀다.

⚠️ **주의: robots.txt 로 막으면 안 된다.** `Disallow: /` 를 걸면 크롤러가 페이지를 아예
안 읽어서 `noindex` 를 못 보고, 오히려 주소만 검색에 남을 수 있다. 그래서 robots.txt 는
일반 검색엔진에 `Allow: /` 를 유지하고, 검색 차단은 메타 태그로만 한다.
`robots.txt` 안의 "일반 검색엔진은 환영합니다" 주석도 이 이유를 적어 정정했다.

### 2. `robots.txt` 는 여전히 무효 — 사용자 선택 대기

크롤러는 도메인 맨 앞만 읽는데 우리 파일은 `.../gloudy/robots.txt` 라 404 다.
넣을 내용은 `docs/robots-root.txt` 로 준비해 뒀다(맨 위에 경고 주석 포함).

| 나. 그 이름으로 **새 저장소**를 만들어 robots.txt 만 넣기 | 지금 주소 그대로 | 저장소가 2개가 된다 |

## 2026-09-01 (2) — 전체 검수 후 디자인 개선 1단계

**배경** 2026년 포트폴리오·랜딩페이지 트렌드를 조사해 현재 사이트와 대조했다.
다크+액센트 1색, 미니멀, 큰 타이포, CLS 방어, 접근성은 **이미 기준에 부합**했다.

### 발견 — 사진이 53px 로 표시되고 있었다

작업 카드가 `제목 → 설명 → 작은 썸네일 5개` 순서라, 사진 한 장이
**데스크톱 53×53px / 모바일 84px** 로 보였다. 파일은 560~700px 이므로 **13배 과대 전송**.
사진가 포트폴리오인데 작품이 우표 크기였고, 모든 트렌드 자료가 말하는
"work first" 원칙과 정반대였다.

### 조치

| 항목 | 전 | 후 |
|---|---|---|
| 카드 구조 | 제목→설명→썸네일 5개 | **대표 사진 1장(크게) → 제목→설명** |
| 사진 표시 (PC) | 53×53 | **336×224** |
| 사진 표시 (모바일) | 84 | **277** |
| 첫 화면 이미지 | 92장 3.77MB | **24장 0.90MB (-76%)** |
| HTML | 77KB | 65KB |
| 최대 폭 | 무제한 | **1560px** |
| 중단점 | 800px 하나 | 640 / 1180 / 800px |
| 폰트 | CSS `@import` (렌더 차단) | `<link>` + `preconnect` |
| 건너뛰기 링크 | 없음 | 추가 (fixed, 포커스 시 슬라이드) |
| 빈 `<img src="">` | 있음 | 제거 |

전체 사진은 커버를 누르면 기존 라이트박스에서 그대로 다 볼 수 있다.
장수는 커버 오른쪽 아래 배지(`13장`)로 표시된다.

### 디자이너 시점 재검수에서 나온 2차 문제

첫 적용에서 커버를 **4:3 고정**으로 했더니 **포스터가 40% 잘려나갔다.**
측정해보니 사진 17장은 3:2 가로, 포스터 3장은 4:5 세로, 로고 1장은 1:1 이었다.
→ 이미지 실제 비율을 읽어 `data-ratio="wide|square|tall"` 을 심고
프레임을 각각 3:2 / 1:1 / 4:5 로 나눴다. **평균 잘림 19.6% → 1.3%.**

### 검증

| 항목 | 결과 |
|---|---|
| 콘솔 오류 | 0 |
| 커버 클릭·Enter·Space → 라이트박스 | 전부 열림 |
| 카운터 / 다음·이전 / 순환 / ESC / 스크롤 복구 | 정상 |
| 필터 (전체24·사진20·디자인4), 히어로 탭 | 정상 |
| 모바일 메뉴 (열기·배경·항목클릭 닫힘·ESC) | 정상 |

### 검사 환경에서 겪은 함정

미리보기 창이 `document.visibilityState === 'hidden'` 이면 **CSS 전환이 얼어붙는다.**
이 때문에 모바일 메뉴가 열리지 않는 것처럼 보였고(`transform` 이 시작값에 고정),
`:focus` 스타일도 적용되지 않으며(`document.hasFocus()` false), 스크린샷도 빈 화면이 나온다.
→ **`*{transition:none!important}` 를 주입한 뒤 측정**해야 실제 동작을 볼 수 있다.
셋 다 사이트 결함이 아니었다.

### 같은 날 — 개선 2단계: AVIF 도입

**WebP 는 불가, AVIF 는 가능했다.** 이 맥에는 `cwebp`/`magick`/`ffmpeg` 가 없고
`sips` 도 webp 를 못 만든다. 반면 CoreGraphics 는 `public.avif` 인코딩을 지원한다
(`CGImageDestinationCopyTypeIdentifiers` 로 확인). AVIF 가 WebP 보다 압축률도 좋다.

**저작권 문제를 변환 단계에서 해결했다.** 재인코딩하면 저작권 정보가 지워지는 것이
기존 규칙의 골칫거리였는데, `CGImageDestinationAddImage` 에 TIFF/IPTC 딕셔너리를
같이 넘기면 **변환하면서 바로 심긴다.** 사후 삽입이 필요 없다.

| 항목 | 전 | 후 |
|---|---|---|
| 첫 화면 커버 24장 | 0.90 MB | **0.41 MB (−54%)** |
| 라이트박스 사진 1장 | 375 KB | **140 KB (−63%)** |
| images/full 전체 | 58.6 MB | 21.9 MB |
| images/thumb 전체 | 4.1 MB | 1.9 MB |
| 변환 실패 | — | **0장 / 264장** |
| AVIF 저작권 정보 | — | **264/264 포함** |

1단계와 합치면 **첫 화면 3.77MB → 0.41MB (−89%)**.

**연결 방식**
- 커버: `<picture><source type="image/avif"><img src="기존파일"></picture>`
- 라이트박스: **AVIF 를 먼저 시도하고 `onerror` 로 원본 복귀.**
  처음엔 비동기 지원 감지(`avifOK`)로 분기했는데, 감지가 끝나기 전에 첫 장이 열려
  JPEG 가 나갔다. 감지를 기다리지 않는 지금 방식이 확실하다.
- 기존 JPEG/PNG 는 **폴백용으로 전부 보존** (저장소 93MB → 117MB, Pages 한도 1GB)

**검증**

| 항목 | 결과 |
|---|---|
| 커버 24장이 실제로 받는 포맷 | avif 24 / 깨짐 0 |
| 라이트박스 (사진·포스터) | `ocsu_0.avif` 1600px · `aug_poster_0.avif` 1280×1600 |
| 폴백 (avif 를 일부러 지우고 시험) | 404 → `ocsu_5.jpg` 자동 로드, 화질 손실 없음 |
| 워터마크 보존 (오른쪽 아래 픽셀 비교) | 평균 색차 0.5~1.5/255, 질감 편차 동일 |
| 라이트박스 열기/키보드/필터/스크롤 복구 | 전부 정상 |
| 콘솔 오류 | 0 (남아 있던 404 는 `favicon.ico` 였고 추가해 해결) |

**곁다리로 고친 것** 브라우저가 자동 요청하는 `/favicon.ico` 가 계속 404 였다.
기존부터 있던 문제. `favicon-32.png` 를 복사해 넣어 해결.

**도구** `tools/to_avif.swift` + `tools/to_avif.sh` 추가.

### 같은 날 — 조직 규모 표기 철회 (푸시 전 발견)

`대표 포함 2인 조직` 은 **틀린 정보였다.** 실제 구조는 다음과 같다.

```
대표
├─ 사용자        기획 · 마케팅 · 브랜딩 · 공간
└─ 카페          총괄매니저 2명 + 아르바이트생
```

최소 4명 + 아르바이트다. 사용자가 "우리는 2인"이라고 한 것은 **사무·기획 파트** 기준이었는데
이를 조직 전체 규모로 오해해 문서에 넣었다. 면접에서 되물으면 바로 무너지는 문장이었다.

| 위치 | 전 | 후 |
|---|---|---|
| 기간 칸 | 대표 포함 2인 조직 | **기획·브랜딩 전담 1인** |
| 직무 큰 줄 | · 운영 | **· 공간 운영** |
| 담당 업무 1 | 리모델링과 **운영**을 맡았습니다 | 리모델링을 맡았습니다 |

사용자는 카페의 **매출·재고·인력 등 현장 운영에 관여하지 않는다**(2026-09-01 확인).
아르바이트 채용은 대표와 총괄매니저가 한다 → **인력 운영 항목은 넣지 않기로 함.**

**조직 규모 대신 역할 범위로 밀도를 표현하는 쪽이 낫다.** 인원 수는 늘고 줄지만
"기획·브랜딩 전담 1인"은 변하지 않고, 되물어도 답이 막히지 않는다.

남은 `운영` 표현 5곳은 전수 확인함 — 공간 운영 / 행사 현장 운영 / 교육 보조 등
전부 실제 담당 범위 안이라 그대로 둔다.

**검증** 콘솔 오류 0 · 1280px 가로 넘침 0 · `2인` 문자열 잔존 0
