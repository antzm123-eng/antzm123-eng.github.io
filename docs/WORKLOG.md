## 2026-09-01 (2) — 전체 검수 후 디자인 개선 1단계

**배경** 2026년 포트폴리오·랜딩페이지 트렌드를 조사해 현재 사이트와 대조했다.
다크+액센트 1색, 미니멀, 큰 타이포, CLS 방어, 접근성은 **이미 기준에 부합**했다.
문제는 딱 하나였다.

### 발견 — 사진이 53px 로 표시되고 있었다

작업 카드가 `제목 → 설명 → 작은 썸네일 5개` 순서라, 사진 한 장이
**데스크톱 53×53px / 모바일 84px** 로 보였다. 파일은 560~700px 이므로 **13배 과대 전송**.
사진가 포트폴리오인데 작품이 우표 크기였고, 모든 트렌드 자료가 말하는
"work first" 원칙과 정반대였다.

### 조치

| 항목 | 전 | 후 |
|---|---|---|
| 카드 구조 | 제목→설명→썸네일 5개 | **대표 사진 1장(크게) → 제목→설명** |
| 사진 표시 (PC) | 53×53 | **336×224** |
| 사진 표시 (모바일) | 84 | **277** |
| 첫 화면 이미지 | 92장 3.77MB | **24장 0.90MB (-76%)** |
| HTML | 77KB | 65KB |
| 최대 폭 | 무제한 | **1560px** |
| 중단점 | 800px 하나 | 640 / 1180 / 800px |
| 폰트 | CSS `@import` (렌더 차단) | `<link>` + `preconnect` |
| 건너뛰기 링크 | 없음 | 추가 (fixed, 포커스 시 슬라이드) |
| 빈 `<img src="">` | 있음 | 제거 |

전체 사진은 커버를 누르면 기존 라이트박스에서 그대로 다 볼 수 있다.
장수는 커버 오른쪽 아래 배지(`13장`)로 표시된다.

### 디자이너 시점 재검수에서 나온 2차 문제

첫 적용에서 커버를 **4:3 고정**으로 했더니 **포스터가 40% 잘려나갔다.**
측정해보니 사진 17장은 3:2 가로, 포스터 3장은 4:5 세로, 로고 1장은 1:1 이었다.
→ 이미지 실제 비율을 읽어 `data-ratio="wide|square|tall"` 을 심고
프레임을 각각 3:2 / 1:1 / 4:5 로 나눴다. **평균 잘림 19.6% → 1.3%.**

### 검사 환경에서 겪은 함정

미리보기 창이 `document.visibilityState === 'hidden'` 이면 **CSS 전환이 얼어붙는다.**
이 때문에 모바일 메뉴가 열리지 않는 것처럼 보였고(`transform` 이 시작값에 고정),
`:focus` 스타일도 적용되지 않으며(`document.hasFocus()` false), 스크린샷도 빈 화면이 나온다.
→ **`*{transition:none!important}` 를 주입한 뒤 측정**해야 실제 동작을 볼 수 있다.
셋 다 사이트 결함이 아니었다.

### 같은 날 — 개선 2단계: AVIF 도입

**WebP 는 불가, AVIF 는 가능했다.** 이 맥에는 `cwebp`/`magick`/`ffmpeg` 가 없고
`sips` 도 webp 를 못 만든다. 반면 CoreGraphics 는 `public.avif` 인코딩을 지원한다
(`CGImageDestinationCopyTypeIdentifiers` 로 확인). AVIF 가 WebP 보다 압축률도 좋다.

**저작권 문제를 변환 단계에서 해결했다.** 재인코딩하면 저작권 정보가 지워지는 것이
기존 규칙의 골칫거리였는데, `CGImageDestinationAddImage` 에 TIFF/IPTC 딕셔너리를
같이 넘기면 **변환하면서 바로 심긴다.** 사후 삽입이 필요 없다.

| 항목 | 전 | 후 |
|---|---|---|
| 첫 화면 커버 24장 | 0.90 MB | **0.41 MB (−54%)** |
| 라이트박스 사진 1장 | 375 KB | **140 KB (−63%)** |
| images/full 전체 | 58.6 MB | 21.9 MB |
| images/thumb 전체 | 4.1 MB | 1.9 MB |
| 변환 실패 | — | **0장 / 264장** |
| AVIF 저작권 정보 | — | **264/264 포함** |

1단계와 합치면 **첫 화면 3.77MB → 0.41MB (−89%)**.

**연결 방식**
- 커버: `<picture><source type="image/avif"><img src="기존파일"></picture>`
- 라이트박스: **AVIF 를 먼저 시도하고 `onerror` 로 원본 복귀.**
  처음엔 비동기 지원 감지(`avifOK`)로 분기했는데, 감지가 끝나기 전에 첫 장이 열려
  JPEG 가 나갔다. 감지를 기다리지 않는 지금 방식이 확실하다.
- 기존 JPEG/PNG 는 **폴백용으로 전부 보존** (저장소 93MB → 117MB, Pages 한도 1GB)

**검증**

| 항목 | 결과 |
|---|---|
| 커버 24장이 실제로 받는 포맷 | avif 24 / 깨짐 0 |
| 라이트박스 (사진·포스터) | `ocsu_0.avif` 1600px · `aug_poster_0.avif` 1280×1600 |
| 폴백 (avif 를 일부러 지우고 시험) | 404 → `ocsu_5.jpg` 자동 로드, 화질 손실 없음 |
| 워터마크 보존 (오른쪽 아래 픽셀 비교) | 평균 색차 0.5~1.5/255, 질감 편차 동일 |
| 라이트박스 열기/키보드/필터/스크롤 복구 | 전부 정상 |
| 콘솔 오류 | 0 (남아 있던 404 는 `favicon.ico` 였고 추가해 해결) |

**곁다리로 고친 것** 브라우저가 자동 요청하는 `/favicon.ico` 가 계속 404 였다.
기존부터 있던 문제. `favicon-32.png` 를 복사해 넣어 해결.

**도구** `tools/to_avif.swift` + `tools/to_avif.sh` 추가.
새 작업물을 `add_work.py` 로 넣은 뒤 `bash tools/to_avif.sh` 한 번 돌리면 된다.
(이미 .avif 가 있는 파일은 건너뛴다.)

### 같은 날 — 배포 후 전수 검수에서 발견한 반응형 빈틈

사진이 597px 로 커지는** 현상을 발견했다. 1단계에서 내가 만든 빈틈이었다.

663px 인데 2칼럼은 `320×2+24=664px` 가 필요해 **1px 차이로** 1칼럼이 됐다.

### 같은 날 — 조직 규모 표기 철회 (푸시 전 발견)

`대표 포함 2인 조직` 은 **틀린 정보였다.** 실제 구조는 다음과 같다.

```
대표
├─ 사용자        기획 · 마케팅 · 브랜딩 · 공간
└─ 카페          총괄매니저 2명 + 아르바이트생
```

최소 4명 + 아르바이트다. 사용자가 "우리는 2인"이라고 한 것은 **사무·기획 파트** 기준이었는데
이를 조직 전체 규모로 오해해 문서에 넣었다. 면접에서 되물으면 바로 무너지는 문장이었다.

| 위치 | 전 | 후 |
|---|---|---|
| 기간 칸 | 대표 포함 2인 조직 | **기획·브랜딩 전담 1인** |
| 직무 큰 줄 | · 운영 | **· 공간 운영** |
| 담당 업무 1 | 리모델링과 **운영**을 맡았습니다 | 리모델링을 맡았습니다 |

사용자는 카페의 **매출·재고·인력 등 현장 운영에 관여하지 않는다**(2026-09-01 확인).
아르바이트 채용은 대표와 총괄매니저가 한다 → **인력 운영 항목은 넣지 않기로 함.**

**조직 규모 대신 역할 범위로 밀도를 표현하는 쪽이 낫다.** 인원 수는 늘고 줄지만
"기획·브랜딩 전담 1인"은 변하지 않고, 되물어도 답이 막히지 않는다.

남은 `운영` 표현 5곳은 전수 확인함 — 공간 운영 / 행사 현장 운영 / 교육 보조 등
전부 실제 담당 범위 안이라 그대로 둔다.

**검증** 콘솔 오류 0 · 1280px 가로 넘침 0 · `2인` 문자열 잔존 0
